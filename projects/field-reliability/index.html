What was wrong

A robot that does the right thing ninety-five times in a hundred is a robot somebody has to watch. The other five are rarely about the clever parts. A clock that is wrong at power-on. A sensor that slows down without stopping. A second copy of the software that started by accident. A log so large it never leaves the site.

None of this is glamorous and all of it decides whether the clever parts get used.

What I built

  • A simulator that runs the real thing. The articulated robot in simulation runs the same software and robot configuration as the machine, on simulated hardware, and the test scenarios drive it the way an operator would. A unit test passing is not the bar; the whole robot doing the job is.
  • A regression suite, from nothing. It covers the whole stack, and bugs found on robots come back as tests.
  • Robots that refuse. If a sensor is unhealthy or the robot does not know where it is, it will not start a job, and it tells the operator why in plain words.
  • A black box. Every start-up is recorded so that a failure on a site a thousand kilometres away can be investigated afterwards.
  • Logs that fit through a bad network. Repeated values are no longer written, and the signals that were thinned can still be reconstructed.
  • A manual-driving fix. A remote-control oscillation could turn a machine through 238 degrees with the stick centred on average. Found from logs, reproduced, removed.

Leading it

A stack is only as good as what is allowed onto a robot. I run that: four releases in 2026, planned, tested and rolled out to the machines in the field in India and the UAE. I wrote the roadmap the autonomy team is building against through 2027. I mentor four engineers, and I wrote the checklists a robot has to pass before it goes to a customer.
